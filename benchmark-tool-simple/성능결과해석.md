# 성능 벤치마크 결과 해석 가이드

`vllm-result/` 아래 JSON 결과는 vLLM `benchmark_serving.py` 포맷이다. 이 문서는 해당 결과를 어떻게 읽어야 하는지 정리한다.

## 핵심 지표

| 지표 | 의미 | 좋은 방향 |
|---|---|---|
| **TTFT** (Time To First Token) | 요청 전송 후 첫 토큰이 나오기까지 걸린 시간 | 낮을수록 좋음 (체감 응답성) |
| **TPOT** (Time Per Output Token) | 첫 토큰 이후, 토큰 1개 생성에 걸리는 평균 시간 | 낮을수록 좋음 (생성 속도) |
| **ITL** (Inter-Token Latency) | 실제 토큰 간 간격 (TPOT과 유사하나 실측 기반) | 낮고 분산이 작을수록 좋음 |
| **E2E Latency** | 요청 전체 완료까지 걸린 시간 (TTFT + TPOT × 출력 토큰 수) | 낮을수록 좋음 |
| **Throughput** (output / total token) | 초당 시스템이 처리하는 토큰 수 | 높을수록 좋음 |
| **power_consumption** | 측정 구간의 전력 소비 | NPU 효율(throughput/W) 비교에 사용 |

- `mean_*`, `median_*`(=p50), `p25/50/75/90/95/99_*` 형태로 분포가 제공된다.
- p50(중앙값)만 보지 말고 **p90/p99를 함께 확인**해야 한다. 꼬리가 길면 "가끔 느린 요청"이 존재한다는 뜻이며, 실사용 체감 품질은 꼬리 값이 좌우한다.

## concurrency(동시 요청 수)와 트레이드오프

결과 폴더명은 `{input_tokens}.{output_tokens}.{concurrency}` 형식이다 (예: `1024.1024.8` = 입력 1024 토큰, 출력 1024 토큰, 동시 요청 8개).

실제 측정 예시 (Qwen3-8B-FP8, input/output 1024 토큰):

| concurrency | output throughput | TTFT p50 | TPOT p50 | E2E p50 |
|---|---|---|---|---|
| 1  | 102.8 tok/s  | 24ms  | 9.7ms  | 9.96s |
| 8  | 656.1 tok/s  | 104ms | 12.1ms | 12.5s |
| 32 | 1480.6 tok/s | 185ms | 21.5ms | 22.1s |
| 64 | 1797.0 tok/s | 205ms | 35.4ms | 36.4s |

**해석 포인트:**

1. **처리량 vs 지연은 트레이드오프다.** concurrency를 올리면 전체 처리량(tok/s)은 증가하지만, 개별 요청의 TTFT/TPOT/E2E는 길어진다. 서버가 여러 요청을 배치로 묶어 처리하기 때문이다.
2. **변곡점(knee point)을 찾는다.** 위 데이터에서 1→8은 throughput이 6.4배 늘었는데 TTFT는 4배만 늘어 효율적이다. 반면 32→64는 throughput이 1.2배만 늘었는데 TPOT은 1.6배 느려졌다 — 포화(saturation)에 가까워졌다는 신호다. 이 데이터 기준으로는 **concurrency 32 부근이 처리량 대비 지연의 균형점**으로 보인다.
3. **용도에 따라 중요 지표가 다르다.**
   - 챗봇/실시간 대화: TTFT, TPOT(체감 끊김)이 중요 → concurrency를 낮게 유지
   - 배치 처리/오프라인 요약: throughput이 중요 → concurrency를 높여서 처리
4. **전력 효율도 함께 본다.** `power_consumption`을 함께 기록하므로 throughput/W로 NPU 효율을 비교할 수 있다.

## 대시보드 활용 팁 (`benchmark_dashboard.py`)

- `동시 요청 수별 성능 비교` 차트에서 metric을 `output_throughput`과 `mean_tpot_ms`(또는 `p99_tpot_ms`) 두 가지로 번갈아 보면서, concurrency 축 위에서 두 곡선이 교차하거나 꺾이는 지점을 확인하는 것이 가장 빠른 해석 방법이다.
- 반복 측정(같은 run/concurrency에 파일이 여러 개)은 평균으로 표시되므로, 변동성이 큰 경우 원본 파일을 개별 확인한다.
- p50 대신 p99 지표를 선택해 비교하면 "최악의 경우" 성능 저하를 더 잘 드러낼 수 있다.

## "비교할 측정 항목" 드롭다운 전체 목록

드롭다운은 JSON/CSV에서 숫자형으로 파싱되는 모든 컬럼을 보여준다. 현재 데이터 기준 전체 59개 항목은 다음과 같다.

### 요청/실험 설정값

| 항목 | 의미 |
|---|---|
| `num_prompts` | 이번 실행에서 보낸 전체 요청(프롬프트) 개수 |
| `request_rate` | 초당 요청 전송 목표 비율 (`inf`면 제한 없이 동시에 전부 전송) |
| `burstiness` | 요청 전송 간격의 변동성 (1.0 = 포아송 분포 기본값) |
| `max_concurrency` | 동시에 허용한 최대 요청 수 (폴더명의 concurrency와 동일 값) |
| `duration` | 벤치마크 전체 실행 시간 (초) |
| `completed` | 정상적으로 완료된 요청 수 |
| `total_input_tokens` | 전체 요청의 입력 토큰 합계 |
| `total_output_tokens` | 전체 요청의 출력 토큰 합계 |

### 처리량 (Throughput) — 높을수록 좋음

| 항목 | 의미 |
|---|---|
| `request_throughput` | 초당 처리한 요청 수 (req/s) |
| `output_throughput` | 초당 생성한 출력 토큰 수 (tok/s) |
| `total_token_throughput` | 초당 처리한 입력+출력 토큰 합계 (tok/s) |

### TTFT — Time To First Token (낮을수록 좋음, 체감 응답성)

| 항목 | 의미 |
|---|---|
| `mean_ttft_ms` | 첫 토큰까지 걸린 시간의 평균 |
| `median_ttft_ms` | 중앙값 (`p50_ttft_ms`와 동일) |
| `std_ttft_ms` | 표준편차 (값이 클수록 요청 간 편차가 큼) |
| `p25/p50/p75/p90/p95/p99_ttft_ms` | 백분위수. p50=전형적인 경우, p99=가장 느린 1% |

### TPOT — Time Per Output Token (낮을수록 좋음, 생성 속도)

| 항목 | 의미 |
|---|---|
| `mean_tpot_ms` | 첫 토큰 이후 토큰 1개당 평균 생성 시간 |
| `median_tpot_ms`, `std_tpot_ms` | 중앙값, 표준편차 |
| `p25/p50/p75/p90/p95/p99_tpot_ms` | 백분위수 |

### ITL — Inter-Token Latency (낮고 분산 작을수록 좋음)

| 항목 | 의미 |
|---|---|
| `mean_itl_ms` | 실측 토큰 간 간격의 평균 (TPOT과 유사하나 실측치) |
| `median_itl_ms`, `std_itl_ms` | 중앙값, 표준편차 |
| `p25/p50/p75/p90/p95/p99_itl_ms` | 백분위수 |

### E2E Latency — End-to-End (낮을수록 좋음, 요청 전체 소요 시간)

| 항목 | 의미 |
|---|---|
| `mean_e2el_ms` | 요청 시작부터 완료까지 전체 시간의 평균 |
| `median_e2el_ms`, `std_e2el_ms` | 중앙값, 표준편차 |
| `p25/p50/p75/p90/p95/p99_e2el_ms` | 백분위수 |

### Power Consumption (vLLM 리포트 기준, 요청 단위)

| 항목 | 의미 |
|---|---|
| `mean_power_consumption` | 요청 처리 중 전력 소비 평균 |
| `median_power_consumption`, `std_power_consumption` | 중앙값, 표준편차 |
| `p25/p50/p75/p90/p95/p99_power_consumption` | 백분위수 |

### NPU 모니터링 CSV 기반 (`csv.mean.*`)

CSV 파일은 벤치마크 실행 중 일정 주기로 NPU 상태를 측정한 시계열(timestamp별 기록)이며, 여러 행을 평균 내어 하나의 값으로 들어간다.

| 항목 | 의미 |
|---|---|
| `csv.mean.utilization` | NPU 사용률 평균 (%) |
| `csv.mean.power_consumption` | NPU 전력 소비 평균 (W) — JSON의 `mean_power_consumption`(요청 단위 추정치)과는 출처가 다른 실측값 |
| `csv.mean.temperature` | NPU 온도 평균 (°C) |

> 실무에서 가장 자주 보는 조합: `output_throughput`(처리량) + `p99_ttft_ms`(최악의 응답 지연) + `csv.mean.power_consumption`(전력 효율)을 함께 비교하면, 성능·지연·전력을 모두 고려한 concurrency 설정점을 찾기 쉽다.
